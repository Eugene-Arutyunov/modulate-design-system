Design Review with an AI Agent

A design review starts with a few practical questions: which screens need checking, where are their prototypes, and what’s different in production? As the product grows, keeping track of all that becomes part of the work.

Going through every screen with a ruler takes time. Leaving feedback in chat means eventually hunting down which page each comment referred to. I wanted an agent to handle the first pass, but it needed the same context I did: what to review, what to compare it with, and where to keep the findings. That led to two sections:

  • The UI Scheme provides the map: it lists the product’s screens and connects their prototypes with the corresponding pages in production. It gives us a place to see what the interface consists of and choose what to review.
  • Compare is where the review itself lives. It puts prototype and production screenshots side by side, alongside the differences and suggested fixes. The map helps us find a screen; the comparison helps us decide what needs to change.

One Problem, Several Screens

Say the subtitle color is wrong on ten pages. You can leave ten comments, but then someone has to work out whether those are ten separate fixes or one shared style.

In Compare, that can be one issue: the color used in the prototype, the color used in production, and a recommendation for the shared style. The affected screens sit below it, so you can check whether the same recommendation really applies to all of them.

That’s why there are separate Issues and Pages views. On a page, the prototype sits on the left and production on the right, with notes underneath and links to shared issues. The Components view does the same for smaller pieces and their states, such as an open account menu.

Of course, two screenshots can look different even when the styling is correct. A table may contain different data; a user may have different permissions. Those differences go into Data diff, so they can be considered separately during review.

One Pass, Two Results

Scheme and Compare share the same update workflow.

The agent opens a page, anonymizes sensitive information where needed, takes a screenshot, and describes the differences it finds. Prepared images are reviewed before publication.

If the page structure also differs from what’s recorded in Scheme, that gets updated too. One pass through the product produces both an updated interface map and material for visual review.

Then I can refine the findings with a regular message:

The subtitle color differs on these pages. Group it as one issue and recommend using the shared style from the prototype.

The agent updates the review. I can check the result and correct it again without rewriting each page’s notes myself.

What Still Needs a Human

The agent gathers screenshots, describes differences, and organizes the findings. I check whether those findings make sense: is this a styling mistake, a different screen state, or an intentional change?

For the subtitle example, I still need to confirm that those pages should use the same style before recommending a shared fix. If the agent grouped them incorrectly, I explain the distinction and ask it to revise the issue. Those corrections also help refine the instructions for the next review.
