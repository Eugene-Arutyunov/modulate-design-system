Compare: Bringing the Prototype and Production Together

Abstract

Prototype, production, and review notes in one place. How Compare connects shared issues to individual screens, and how an agent helps keep the review and the UI Scheme up to date.

I updated the production column in the UI Scheme and built Compare — an all-in-one page for reviewing the prototype against the live product.

The motivation was laziness. Going through every screen with a ruler takes time, and leaving feedback in chat means eventually hunting down which page each comment referred to. I wanted the intended design, the actual implementation, and the suggested fixes in one place. With an agent handling the first pass.

Three Levels of Comparison

Compare has three sections: Issues, Pages, and Components. They let you move between individual screens and problems that repeat across the product.

Issues collects shared problems. When the same style differs across several pages, you can describe it once: what the prototype uses, what production uses, and how to fix it. An expandable list below each recommendation links to the affected screens.

This makes the scope visible and helps identify where the fix belongs. Instead of ten comments about subtitle color, you get one recommendation for the shared style, linked to every example.

Pages puts screens face to face. Prototype on the left, production on the right, with specific differences described below the screenshot. Linked issues connects each screen to the shared problems.

Data diff separately records differences in content, permissions, or screen state. A different number in a table or an empty list doesn’t necessarily mean the interface was implemented incorrectly. That context belongs alongside the review.

There’s also Pixel diff, but it isn’t useful yet. Different data and screen states introduce too much noise. For now, a description of what actually differs is much more helpful.

Components covers individual components and their states, such as an open account menu. These need reviewing too, so they get their own section with the same comparison layout.

One Pass, Two Results

One of my favorite parts: Scheme and Compare share the same update workflow.

The agent opens a page, anonymizes sensitive information where needed, takes a screenshot, and describes the differences it finds. Prepared images are reviewed before publication.

If the page structure also differs from what’s recorded in Scheme, that gets updated too. One pass through the product produces both an updated interface map and material for visual review.

Then I can refine the findings with a regular message:

These things differ across several pages. It’s a shared problem, and this is how it should work.

The agent records the issue and links it to the relevant screens. The recommendation stays connected to its examples, and each page links back to the shared fix.

Why I Like This Setup

You can navigate both ways: from a particular screen to a shared cause, or from a shared problem to every place it appears. Screenshots, observations, and recommendations stay connected, so there’s less context to reconstruct each time.

It still needs human review. I’ll still be checking things by eye. But the machine can handle the first pass, and I can keep refining its instructions: what to look for, what counts as a problem, and which differences come from the data.

Basically, being too lazy to crawl through screens with a ruler turned out to be a good reason to build a tool. Now there’s one place to inspect the differences, discuss them, and keep the results.
